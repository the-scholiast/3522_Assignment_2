## 1. Description

You will produce an object oriented implementation of the Traveling Salesperson Problem (TSP) using a genetic algorithm.

Given an unordered set of cities, we want to visit all of them in a sequence (a tour) that minimizes total travel distance, then return to the starting city. With a small number of cities this is trivial, but the number of possible tours grows as `n!`, so brute force becomes impractical past a few dozen cities (see `slides.pdf`, "Travelling salesperson problem"). A genetic algorithm is a heuristic, inspired by natural selection, that searches for a good (not necessarily optimal) tour in a reasonable amount of time: start with a population of candidate tours, evaluate their fitness, perform crossover and mutation, and repeat until the population converges on a good solution or a termination condition is met.

Before starting, optionally, read the accompanying paper `survey.pdf`("Genetic Algorithms, A Survey"). It's a short, interesting read and will give you useful context for the terms and steps below.

## 2. Requirements

Your program must implement an object oriented solution to the following scenario (see `slides.pdf`, "Some terms we are using" for the terminology used below, and "Our algorithm" for a worked walkthrough).

1. A **city** has a name and a set of coordinates, `x` and `y`.
2. Coordinates are limited to the range `[0, 1000]` inclusive (`MAP_BOUNDARY`).
3. A **tour** is a list of cities. A tour contains the entire list of cities and a fitness rating. The fitness rating evaluates the distance the salesperson would travel visiting the cities in the order they appear in the tour.
4. Create a group of cities first. Each city must have a unique name/sequence number and random coordinates.
5. Create a **population** of tours. Each tour contains the entire list of cities, shuffled into a random order. The population is a data structure that manages a collection of tours.
6. Determine and record the fitness of each tour. Fitness is equivalent to distance, as a `double`. Shorter tours have better (lower) fitness.
7. Note the shortest (fittest) tour. This is `base_distance`, the starting point for the algorithm.
8. Implement the genetic algorithm iteratively until `base_distance / best_distance > IMPROVEMENT_FACTOR`:
   - **Selection**: move the fittest tour to the front of the population and leave it unchanged this iteration. This is the "elite" individual.
   - **Crossover**: replace every non-elite tour with a new tour generated by crossing parents. Each parent is the fittest of a randomly selected subset of size `PARENT_POOL_SIZE` from the population. Cross `NUMBER_OF_PARENTS` parents to create each child tour, and repeat until every non-elite tour has been replaced.

     To cross two parents: pick a random index, take the cities from the first parent up to and including that index, then fill the rest of the tour with cities from the second parent in order, skipping any city already added. If more than two parents are crossed, continue through the remaining parents the same way, skipping cities already in the tour.

   - **Mutation**: randomly select 30% of the tours (excluding the elite) to mutate (feel free to change this percentage). For each city in a tour being mutated, roll a random value; if it's less than `MUTATION_RATE`, swap that city with its adjacent city in the tour.
   - **Evaluation**: assign each new tour a fitness value.
   - **Report**: print the algorithm's progress to the user.

9. Implement the Singleton and Facade design patterns via a `SingletonFacade` class that hides the complexity of running the algorithm above. `main()` should get the singleton instance and call a `run()` function to kick off the steps above.
10. Constants and behaviors to consider (not an exhaustive list):

    | Name                 | Suggested value       | Notes                                                                                                     |
    | -------------------- | --------------------- | --------------------------------------------------------------------------------------------------------- |
    | `CITIES_IN_TOUR`     | 32                    | nice to let the user choose                                                                               |
    | `POPULATION_SIZE`    | 32                    | nice to let the user choose                                                                               |
    | `SHUFFLES`           | 64                    | swaps per shuffle if hand-rolling your own swap; 1 shuffle per tour if using the standard library shuffle |
    | `ITERATIONS`         | 1000                  | max iterations                                                                                            |
    | `MAP_BOUNDARY`       | 1000                  | largest legal coordinate                                                                                  |
    | `PARENT_POOL_SIZE`   | 5                     | candidates considered per parent selection                                                                |
    | `MUTATION_RATE`      | 15%                   | nice to let the user choose                                                                               |
    | `NUMBER_OF_PARENTS`  | -                     | number of parent tours crossed per child                                                                  |
    | `NUMBER_OF_ELITES`   | 1                     | try changing this and observe the effect                                                                  |
    | `IMPROVEMENT_FACTOR` | 1.2 (20% improvement) | feel free to increase                                                                                     |

    Functions worth having: `shuffle_cities`, `get_distance_between_cities`, `get_tour_distance`, `determine_fitness`, `select_parents`, `crossover`, `mutate`, `contains_city`, and a way to report `best_distance` (the newest elite's distance).

## FAQ

**After a while, my tours all mutate to be the same path through the cities. How do I fix this?**

This is a common "bug" with no single known cause. One proposed fix is to increase the percentage of tours chosen for mutation (above 30%), which gives a better chance of producing new paths. A second suggestion, used alongside the first, is to prevent duplicate parents from being considered when generating the next generation of tours.
